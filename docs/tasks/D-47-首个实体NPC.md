## 0. 结论

T 键不再是"凭空弹出一个对话框"：F1 地图上真的站着一个人（`warden_f1` / 守夜人·洛恩），必须走到相邻格（含斜向）按 T 才打开任务面板；距离 >1 只给一行非阻塞提示「附近没有人」。任务是"探路"——走到下行梯旁再回来复命，四态互斥（unaccepted → active → ready → done），交付固定 60 金币、重复交付不加钱；`reward.exclusiveItem` 只留数据口，本卡不发装备。

同种子 1001–1050 / maxActions 2500：**B1 默认支路 7/50 与 D-46 逐局完全一致**（G2 19、S1 25、M1 到 F4 29 不变），NPC 支路 50 局**接取 50、交付 50、交互失败 0**，通关仍 7/50（赢的种子换了一批，F5 到达 25→29）。`verify_d47` A–H 全绿，`page-baseline` 87→88，全量回归两轮 88/88、GUARD `expected=88 actual=88`。

## 1. 现状与设计

### 1.1 改前问题

`main.js` 的 T 分支直接 `Game.Systems.NPC.open()` 并切 `_scene='npc'`：地图上没有任何实体，对话框却随时能开——"没有实体的对话框不成立"。

### 1.2 NPC 在哪、怎么保证可达

- 数据：`js/data/npcs.js` 的 `Game.Data.NPCS.list`，当前只有一条 `warden_f1`（floor 1）。
- 取点（`map.js#placeNpc`）：取"出生点→下行梯"的 BFS 主路（优先把怪当墙），在 **72%** 处开始向两侧逐格扫描；主路没有合法格时，按行序扫描整个**出生点连通块**。
- 合法性（`npcCellOk`）：地板格、在出生点连通块内（与 D-38 的真实移动语义一致：会换层的楼梯不当走廊）、不等于出生点、离出生点曼哈顿 ≥4、离下行梯 ≥2、不在密室/密室门、不占敌人/巡逻怪/装饰（含宝箱与 D-46 奖励点）/陷阱。NPC 格本身**仍是可通行地板**，不写入任何阻挡。
- 确定性：全程 0 次 `Math.random`，因此与 D-46 相比，地图/怪物/宝箱/奖励点/陷阱**逐格不变**（E 组用开/关 NPC 的指纹对照证明）。
- 50 个种子（1001–1050）全部"有且仅有 1 个 NPC、零违规"；F2–F5 为 0 个。

### 1.3 交互与面板

- `quest.js` 新增 `Game.Systems.NpcQuest`：`nearby(x,y)` 用 Chebyshev 距离 ≤1（含斜向，也包含站在 NPC 格上）判定；`main.js` 的 T 分支先问 `nearby`，有 NPC 才 `Modal.open('npcquest')`，否则只 `ui:notice`「附近没有人」并返回，**不产生任何模态、不切场景**。
- `modal.js` 新增 `npcquest` 面板：显示 NPC 台词、四态、进度、奖励与操作提示；Enter 按状态执行接取/交付，Esc 关闭。
- 渲染（`render.js`）：程序化像素小人（斗篷/腰带/头/提灯）+ 任务感叹号 + 相邻 2 格内的名字与 `T` 提示；不引入新素材。

### 1.4 任务为什么这么设计（一层内可完成）

- 任务：**探路**——"走到第一层下行梯旁查看，然后回来向守夜人复命"，`need=1`。
- NPC 站在主路 72% 处，离下行梯 3~6 步；接取后走到楼梯**相邻格**（Chebyshev=1，不含楼梯格本身，避免直接换层）即达成 ready，回头几步就能交付。
- 不依赖战斗随机数、不依赖商店经济、不要求清怪，因此在 F1 内**必定可完成**；同时天然形成"接取 → 前进 → 返回"的往返，正好验证"必须走到人旁边"这件事。
- 四态由 `accepted / progress / delivered` 推导，天然互斥：`delivered→done`；`!accepted→unaccepted`；`progress≥need→ready`；否则 `active`。

### 1.5 奖励与数据留口

- `quest.reward = { gold: 60, exp: 0, exclusiveItem: null }`。
- 60 来自 D-46 的结论（F1 首店缺口中位 45、F2 79；一次任务给 60 足以补上 F1 缺口而不制造"捡钱模拟器"）。
- `exclusiveItem` 的注释写明了"任务专属装备"的完整结构（id/name/type/effect/price/sell），`deliver` 只读 gold/exp，**不写背包、不写装备栏**。

### 1.6 存档

- 键名 `ai_dungeon_rpg_save_v1` 不变，只加 `player.npcQuests`；楼层快照增加 `npcs`。
- 读档：`npcQuests` 缺失补 `{}`；楼层快照缺 `npcs` 时用同一套确定性规则**原地补生成**并写回缓存（不会误判成"本层没有 NPC"）。

## 4. 五个回答

1. **NPC 站在哪？怎么保证每局都可达？**
   站在"出生点→下行梯"主路 72% 处（离楼梯 3~6 步），沿路径向两侧找第一个合法格；主路找不到就扫描整个出生点连通块。合法性由 `npcCellOk` 统一判定（连通块内、非楼梯/出生点/怪物/巡逻/装饰/陷阱/密室），取点不消耗 `Math.random`。50 个种子实测 50/50 合规，负例把 NPC 放到墙/不可达格会被同一判据判 FAIL。

2. **现在按 T 会发生什么？距离远的时候呢？**
   站在 NPC 相邻格（含斜向）按 T → 打开 `npcquest` 任务面板（状态/进度/奖励/操作）。距离 >1 → 只在底部提示条显示一行「附近没有人」，不弹模态、不切场景、不阻塞输入。旧的"无实体守门人聊天"不再由 T 打开（`Systems.NPC` 仍保留给 M5 的接口与验证页）。

3. **任务为什么这么设计？一层内能完成吗？**
   "探路：走到下行梯旁再回来复命"。NPC 就在通往楼梯的主路上，达成点是楼梯相邻格而不是楼梯格本身（不会一脚踩下去换层），往返只有几步；不依赖战斗/掉落/商店随机数，因此 F1 内必定可完成，同时把"必须走到人旁边"变成任务流程的一部分。

4. **旧档会怎么样？**
   不报错。`player.npcQuests` 缺失补 `{}`（四态从"未接取"开始）；`map.floors[*].npcs` 缺失时按同一确定性规则在已恢复的地图上补生成并写回缓存。F 组用 D-46 结构旧档实测：读入无异常、既有金币/等级保留、NPC 出现、接取与交付（+60）正常。

5. **这个 NPC 和 60 金币，让通关率变了吗？变多少、为什么？**
   默认 B1（不主动找 NPC）**没变：7/50，逐局结果与 D-46 完全一致**。让 bot 真的去接取/交付后仍是 7/50，但到 F5 的局从 25 升到 29，商店购买 211→222 次、支出 +3530 金币；赢的种子换了一批（1004/1016/1036/1043/1044 掉出，1012/1025/1034/1041/1042 进来），说明 60 金币改变了早期购买节奏与随机走向，但**不足以翻越 F4/F5 的血量消耗墙**——通关数没变，变的是"谁走到更远"。
