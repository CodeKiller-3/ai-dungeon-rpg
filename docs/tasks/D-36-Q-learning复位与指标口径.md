## 1. 复位缺陷：`init()` 是唯一入口，必须回到出厂状态

旧实现：

```js
init: function (g) {
  ... Q = 全零; target = ...;
  episode = 0; successes = 0; history = [];
  step = 0;
  // ← epsilon 没有复位
  running = true; reset();
}
```

新实现把 `epsilon`、`recent`（滚动窗口）、`episodeWon` 一并复位，顺序固定为「清状态 → `epsilon = EPS_INIT` → `reset()`」：

```js
episode = 0; successes = 0; history = []; recent = []; episodeWon = false; step = 0;
epsilon = EPS_INIT;      // 0.4
running = true; reset(); // reset 里第一次衰减 → 0.394
```

注意：`init()` 后立刻读到的 ε 是 **0.394**，不是 0.4——因为 `reset()` 在每个 episode 开始时先衰减一次。这是原有衰减曲线，未改。

A 组实测（`verify_d36`，恒等 12×12 网格，种子 11）：

| 场景 | ε | 说明 |
| --- | --- | --- |
| 连续 3 次 `init()` | 0.394 / 0.394 / 0.394 | ε、Q、episode、step、successes、history 长度逐项相等 |
| 训练约 20 轮后再 `init()` | 0.274 → **0.394** | 衰减过的 ε 被拉回初始值，状态与第一次完全一致 |
| 负例：旧 `init`（删掉复位行）同样序列 | **0.268** | 停在衰减值，与第一次不相等 → 断言必须 FAIL |

负例的做法是源码级变异：把生产 `learner.js` 里 `      epsilon = EPS_INIT;\n` 这一行删掉再加载（`INSTR_OLD`），不是另写一份假实现。

## 2. `eval` 绕过的黑历史（按要求留痕）

### 当时为什么绕过

旧 `init()` 不复位 `epsilon`。`verify_c05` 要顺序跑 7 张图，用的是同一个 `Game.Systems.Learner` 单例：

- 第 1 张图：ε=0.4，Q 空 —— 正常；
- 第 2 张图起：Q 被清空，但 ε 已被前一张衰减到 0.05 —— 探索几乎停摆，"同条件对照"不成立。

为了让 7 张图都以"首次进入"的条件起跑，测试页用 `eval` 把 `learner.js` 源码重新执行一遍，**每张图拿一个全新模块实例**。这样 7 张图的数字看起来一致了，但测到的是一个只有测试页才存在的对象。

### 绕过了什么

绕过了**玩家真实路径**：游戏里按 L 永远走 `Game.Systems.Learner` 这一个单例。测试页的"每图新实例"在游戏里不存在，等于用一个不可能发生的场景证明算法没问题，同时把"第二次按 L 就坏"这个真实缺陷留在了产品里。

这正是本项目反复批评的"改测试不改代码"的变体——没有改断言，但改了被测对象。

### 这次怎么翻过来的

1. 修 `init()`（§1），让单例本身具备"每次进入都回到出厂状态"的能力；
2. `freshLearner()` 直接 `return Game.Systems.Learner`，删掉 `eval` 与源码重载；
3. 新增 **C5-6 `singletonReinit`**：7 张图跑完后，用同一种子再 `init` 第 1 张图，`episode` 与 `rate` 必须与第一次逐项相等；
4. C5-6 与 `verify_d36` 的 A/B 组是这条绕过的守门人——谁把 `eval` 加回来、或者把复位行删掉，都会立刻 FAIL。

### 修前绕过值 vs 修后真实值（逐项）

`verify_c05` 同一次运行、同一组种子，修前（`eval` 每图新实例）与修后（单例 + 复位）对照：

| 指标（7 图，seed 101/202/303/404/505/606/707） | 修前（绕过） | 修后（真实） | 是否变化 |
| --- | --- | --- | --- |
| Q 训练期成功率 | 21 / 15 / 13 / 18 / 8 / 6 / 26 | **完全相同** | 无 |
| 随机策略成功率 | 9 / 2 / 4 / 5 / 13 / 2 / 5 | **完全相同** | 无 |
| 每图 episode（3000 步） | 58 / 55 / 54 / 56 / 52 / 52 / 62 | **完全相同** | 无 |
| 中位数（Q / 随机） | 15 / 5 | **15 / 5** | 无 |
| 网格哈希 | b8a46448 / ff3ee8d8 / d565b274 / e96871f0 / 460ff998 / 6d15856c / 4486d74c | **完全相同** | 无 |

结论：移除绕过**没有放宽任何数值**。之所以逐项相同，是因为修好后的 `init()` 让单例每次都以 ε=0.4 起跑，与"新实例"的初始条件本来就该相同——数值不变是缺陷修好的结果，不是断言松了。若只删 `eval` 不修 `init`，第 2 张图起会从 ε=0.05 起跑，episode/rate 必然变化，C5-1 会 FAIL。

## 3. 走势图：图例说"近 20 轮"，数据就必须是近 20 轮

`render.js` 的图例一字未改（仍为「成功率走势（近20轮）」），本卡只改数据源：

```js
// 旧：累计成功率
history.push({ episode: episode, rate: Math.round(successes * 100 / episode) });
// 新：最近 ROLL=20 个 episode 的滚动成功率
recent.push(episodeWon ? 1 : 0);
if (recent.length > ROLL) recent.shift();
history.push({ episode: episode, rate: Math.round(sum(recent) * 100 / recent.length) });
```

C 组用 25 个强制胜负样本（`setState` 摆到目标前一格一步成功 / `step=61` 判超时）逐轮比对：

- 实际画出的 20 根柱 = `history.slice(-20)` 的 rate，逐根相等；
- 25 个值全部等于滚动 20 轮期望；与累计期望在第 21 个样本起分叉（57 vs 55、59 vs 57 …）；
- 负例：把标签改成别的窗口而数据仍是滚动 20，或把数据改回累计，C 组必须 FAIL。

为什么选"改图"而不是"改标签"：演示只有约 10 秒、约 85 轮，累计曲线会被开局几十轮失败永久拖住，越到后面越像一条死线，无法反映"现在学得怎样"；滚动窗口才是演示想表达的东西，而且图例本来就这么写。

## 4. 训练轮数：演示路径与指标路径分账

### 「1478 轮收敛」怎么回答

- 第 1478 轮时 greedy 成功率仍是 **10%~42%**，`ratioOnWins` 1.00~1.11 —— 第三方说的"成功时 12.1 步 vs 12.0 步"在方向上完全复现：**策略一旦成功，走的就是最优路**，从第 25~50 轮起就基本成立（多数图 `ratioOnWins=1.00`）。
- 但"100% 收敛"不成立：3000 episode 无一图达成；加深到 **50000 episode/图**，greedy 成功率 34%~92%，仍无一图覆盖全部可达起点（seed 202 有 4 个不可达起点，天花板 92%）；101 图单训 200000 episode 也只有 72%。
- 因此本项目的结论写成两句话：**"成功时即最优"约几十轮就达到；"全起点成功率"在本协议内不收敛**。难看的是覆盖率，不是策略质量。

### 防止两条路再混回去

1. **物理隔离**：只有一个页面会写 `selfcheck/d36-metrics.json`（`d36_harness.html`）；游戏循环（`main.js` 的 L 场景）从不写证据文件。
2. **命名隔离**：证据里 `trainingRate`（含探索、演示同口径）与 `final.rate`（ε=0、Q 冻结的 greedy 评估）两个字段名不复用；`episodesTrained` 记录真实轮数，演示路径只报 `demoSession`。
3. **复算守门**：`verify_d36` E 组按证据里的 `protocol` 重跑 7 个种子，`gridHash` / `trainingRate` / `epsilonEnd` 任一不等即 FAIL；证据一旦漂移（例如把演示短训数据写进去）会立刻被抓。
4. **文案纪律**：README 与讲稿把「演示路径」「指标路径」分列，并注明演示读数不冒充指标。

## 6. 验收（`preflight/verify_d36.html`）

- **A 组 复位**：连续 3 次 `init()` 的 ε/Q/step/episode/successes/history 长度逐项相等；训练衰减后再 `init` 回到第一次；负例（删掉复位行的旧源码）必须不相等 → 本组 PASS 的前提是负例 FAIL。
- **B 组 二进宫**：同种子 2024，第一次演示前 10 步的坐标轨迹与"跑 30 帧后关掉再进"第二次逐帧相同（`7,6 → … → 8,0`）、ε 同为 0.394；负例把 ε 钉死 0.05 必须判 FAIL。
- **C 组 标签一致**：拦截 `fillRect` 与 `fillText`，20 根柱逐根等于 `history.slice(-20)` 的滚动值；25 个样本与滚动期望全等、与累计期望分叉；图例含「近20轮」。
- **D 组 演示性能**：240 帧 `tick(8)+drawLearner`，P50 0.1ms、P95 0.3ms，预算 16.7ms；另记录 600 帧 = 85 轮。
- **E 组 指标可复算**：读 `selfcheck/d36-metrics.json`，按同协议重跑 7 个种子，`gridHash` / `trainingRate` / `epsilonEnd` 全部相等。

首次运行时 E 组就抓到了真问题：证据页第一版把训练循环留在了 `withSeed` 之外，同一 seed 两次跑出 35% / 39%。修的是证据页（把整段训练包进种子作用域），不是断言。

## 7. 缺口回答

1. **README 成功率会变成多少？** 不变。Q 训练期中位 15%（6%~26%）、greedy 13%（2%~25%）、R1 5%（2%~13%）、R2 7%（2%~13%）、演示快照 88 轮/3%。本卡没有为好看往回凑任何一个数；新增的长训口径单独落在 `d36-metrics.json`，不进 README 的四组基线。
2. **`eval` 黑历史怎么留痕？** 见 §2：写清"当时为什么绕过（旧 init 漏复位导致 7 图条件不一致）、绕过了什么（玩家真实使用的单例路径）、这次怎么翻过来（修 init → 删 eval → 加 C5-6 守门）"，并附修前/修后逐项对照表证明数值未变。
3. **两条路会不会再混？** 见 §4 末尾四条机制：物理隔离（唯一写入者）、命名隔离（`trainingRate` vs `final.rate`）、复算守门（E 组）、文案纪律（README/讲稿分列）。其中 E 组是硬约束：证据只要不是按声明协议跑出来的，验证页立刻 FAIL。
