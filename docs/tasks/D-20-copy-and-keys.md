## 一、按键表：以代码为准，并做机器比对

### 1.1 单一来源

`js/core/render.js` 顶部新增 `KEYMAP`，分 `explore` / `battle` 两张表，每行四个字段：

| 字段 | 含义 |
|---|---|
| `label` | 玩家看到的键名（`1` / `7` / `F` / `Esc` / `↑↓←→ / WASD`） |
| `name` | 该键做什么（`攻击` / `用药` / `重看引导`） |
| `act` | 验证页回放真实按键后要比对的行为标识（`attack` / `item` / `guide`） |
| `codes` | 实际接收的 `KeyboardEvent.code`（`Digit7` / `Numpad7` / `KeyH`…） |

引导页正文由 `KEYMAP` 拼出（`keyLine(scope, line)`），`guideRows()` 再补三条分组标题与五条机制须知。`Render.guideLines()` 把正文导出成纯文本数组，供验证页做机器比对——**画在屏幕上的字和验证页读的字是同一份**。

### 1.2 双向比对（`verify_d20` A1/A2）

- **表 → 码**：表里每一行都用真实 `KeyboardEvent` 回放（`Input` → `Main._updateBattle` / `_updateExplore`），命中声称的行为才算过。战斗 8 行（1–7、F）、探索 9 键（B/E/M/T/L/Q/K/H + 移动四向）逐一回放。
- **码 → 表**：从 `main.js` 的 `_updateExplore` / `_updateBattle` 源码里抽出所有 `k['…']`，从 `input.js` 的 `DIR_CODES` 抽出移动键，**每一个都必须在表里有行认领**。
- **负例**：把 `7 用药` 那一行从表里删掉，同一判定必须 FAIL，且必须指出 `Digit7 / Numpad7` 无人认领。实测：`ok=false`，`missing=["战斗 Digit7 → 表里没有「7」","战斗 Numpad7 → 表里没有「7」"]`。

> 只做"表 → 码"是没有意义的（删一行照样全过）；"码 → 表"才是防遗漏的那一半。

## 八、缺口

1. **机器比对覆盖的是"声明 ↔ 实现"的对应关系，不是语义**。它能证明"表里有 7、代码接 7、回放打出 item"；不能证明"用药"这两个字对玩家是清楚的，也不能证明"半血"的表述与玩家直觉一致。语义要靠人读。
2. **"六处机制有代码"用的是正则证据**，锚定的是关键判定（`hpPct: 0.5`、`lv >= 5`）。若有人改判定为 `0.55` 而文案仍写"半血"，正则只匹配 `0.5` 会 FAIL——这是优点；但若改成 `0.5` 之外的等价写法（如 `hp * 2 <= maxHp`），也会 FAIL（保守误报，需人工确认后改证据）。
3. **感叹号口径只约束标点，不约束语气**。冷峻感还来自句长、用词、是否用"你"，这些本卡没有量化。
4. **故意保留的不统一**：`reactions.js` 的 1 处感叹号（基准）；`胜利！` 与 `升级！`（§4.1）；`README.md` 第 9 行的"Q-learning 强化学习"（D-02 的 `d24` 断言锚定该行文字，且属仓库文档、非游戏内文案）。
5. **按键表覆盖的是"键 → 动作"，不覆盖"动作在什么条件下无效"**。例如战斗中按 `H` 无反应、探索中按 `1` 无反应，表里写的是"该场景可用的键"，场景边界靠玩家自己体会。
