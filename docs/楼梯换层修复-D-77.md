# D-77 · 楼梯换层触发与「楼梯不得单口」修复

> 本卡对应两条玩家可感知症状：①走到下行梯格不换层、必须按「下」；②进入下一层的楼梯只能从一个方向进。
> 结论：症状①是误读（换层判定本来就只看 tile），症状②是真缺陷（地图生成会把楼梯塞进单口死角）。
> 修复方式为用户授权的**方案 B**：楼梯落点确定后，若相邻可走格 ≤1，按固定顺序 N→E→S→W 打开一格邻墙。
> 同时修掉同一流程内的第二个缺陷：**换层落盘早于 `resetPlayer()`**（落盘写的是上一层的梯格坐标）。

---

## 一、根因定位（四条排查方向，逐条给数据）

| 排查方向 | 结论 | 证据 |
| --- | --- | --- |
| 换层判定是否写死按键方向 | **否**。判定只读移动后的 tile 值 | `main.js#_updateExplore`：`t===2 → changeFloor(1)`、`t===3 → changeFloor(-1)`，与按键无关；实测 90/90 逐方向踩梯全部换层（N 20/20、E 25/25、S 21/21、W 24/24） |
| 是否有「就地触发」的独立检测 | **否**。楼梯是即时传送门，没有"站在梯上按某键触发"的分支 | 第 1 层上行梯 / 第 5 层下行梯是唯一的"空转梯"，才会出现"站住"的情况：10/10 空转且不报错；站在空转梯上按 Down 仍能正常走开 |
| 地图生成是否把楼梯塞进单口死胡同 | **是，这是根因** | 修复前 250 张图：下行梯单口 **13/250 = 5.2%**（deg 分布 1:13 / 2:170 / 3:66 / 4:1），上行梯单口 **8/250 = 3.2%**（1:8 / 2:187 / 3:53 / 4:2）；单口朝向 N2/E3/S5/W3 |
| 楼梯格是否被装饰/怪物/精英/NPC 占用 | **否** | 250 张图逐格检查 decor / trap / enemy / npc / elite 在楼梯格上均为 0 |

补充：`placeStairs` 的 `findOpen` 是均匀随机抽样，可落点里 deg≤1 的比例（4.52%）与楼梯单口率一致，
说明这不是 `placeStairs` 的兜底分支，而是"随机落点本身可能落在迷宫叶子上"，因此只能在生成末尾补口。

## 二、方案 B 的实现

### 2.1 位置与顺序

```
carve → openRooms → placeSpecialRoom → placeStairs → spawnEnemies → ensureMandatoryTargets
→ AI.initPatrols → spawn={1,1} → genDetailsAndDecor(decor/traps/rewards → placeElite → placeNpc)
→ ★ ensureStairMouths()          ← D-77 新增
→ floorCache[floor] → emit 'map:floorChanged'
```

调用点放在**所有实体落位之后**（`genDetailsAndDecor` 返回后），原因有两条：

1. 此时所有消耗 `Math.random` 的步骤都已跑完，开一格墙**不会改变任何一次随机抽样**；
2. 不移动、不新增、不删除任何实体 —— 250 张图的实体指纹与修复前逐字相同。

> 曾经试过两个别的落点，都被断言否决，记录在此避免回退：
> · **更早（placeStairs 之后）**：后续 `spawnEnemies` 的抽样接受率变化会让随机流整张图漂移（12 张图 200+ 格差异）。
> · **早于 placeElite**：虽然能让精英在最终 grid 上重算 cut，但它会让 grid 依赖"精英是否存在"，
>   直接踩坏 D-69 A4（精英开关两次生成必须 grid 逐格相同）。

### 2.2 打开条件（自校验，全部是"纯读"后才写）

```
mouthCellOk(c):
  ① 在边界内（1 ≤ x ≤ w-2，1 ≤ y ≤ h-2）
  ② 当前必须是墙（grid===0），绝不覆盖已有地板
  ③ 不在密室"室内 + 四周封墙圈"上（inRoomRing）—— 防止多开一扇门让密室提前暴露
  ④ 无装饰（含 chest / room_chest / gold_pile / potion_stash，奖励点也记在 decor 里）
  ⑤ 无陷阱、无普通怪、无精英、无 NPC、无巡逻怪（Boss 格同理不在候选，因为它不是墙）
写完后再复核：
  ⑥ 新入口必须真的连回出生点连通块（BFS 到该楼梯）—— 排除"只挖出一个 1 格口袋"的假入口
  ⑦ 被动过的 details（墙上苔藓）清空
```

打开顺序固定 **N → E → S → W**，每个楼梯最多补到 deg=2 就停（`guard < 2`）。

### 2.3 不消耗随机数

`ensureStairMouths` 及其全部辅助函数（`stairDegOf` / `inRoomRing` / `mouthCellOk` / `bfsToStair` /
`isCutCell` / `blockedPathLen`）**没有一处调用 `Math.random`**；扫序是常量数组 `[[0,-1],[1,0],[0,1],[-1,0]]`。

### 2.4 上行梯同样处理

F1–F5 的所有 t=2 / t=3 都进同一个循环；只有"另一部楼梯是否真的会换层"这一条按层号区分
（与 `placeStairs.fits` 同语义）：会换层的另一部楼梯不能当走廊穿行，空转梯可以。

## 三、换层存档时序（第二个缺陷）

### 3.1 现状

`changeFloor()` 里 `Map.setFloor()` → `generate()` 末尾 `emit('map:floorChanged')` → `Save.save()`。
此时 `resetPlayer()` 还没执行，`player.x/y` 仍是**上一层梯格坐标**，落盘变成"上一层梯格坐标 + 新层层号"。

### 3.2 修法（`js/core/main.js`）

```js
var deferFloorSave = false;
function onFloorChanged() {
  if (booting) return;
  if (deferFloorSave) return;   /* D-77：踩楼梯换层，落盘推迟到玩家坐标已定之后 */
  Game.Systems.Save.save();
}
/* 换层分支 */
deferFloorSave = true;
try { Map.changeFloor(dir); } finally { deferFloorSave = false; }
resetPlayer();  Adaptive.onFloorArrived();
Save.save();    /* ← 此刻 pos 已是新层出生点 */
```

**未改**：存档键（`ai_dungeon_rpg_save_v1`）、`SAVE_VERSION`、`landableAt`（仍排除 t=0/2/3）、
`resolveLanding`（仍做 BFS 到最近可站立格）、读档不调用 `_updateExplore` 这条语义。

### 3.3 前后坐标实测

| | 落盘内容 |
| --- | --- |
| 修复前（复现旧时序） | `pos = (22,15)，floor=2` ← 第 1 层梯格坐标 + 层号 2 |
| 修复后 | `pos = (1,1)，floor=2` ← 新层出生点，与 `Map.getSpawn()` 一致 |

`verify_d53` 的既有断言未失效：`landableAt` 排除楼梯格这条保留，`resolveLanding` 的 250/250 落点仍全部避开 t=2/3。

## 八、已知取舍

1. **F5 的"空转下行梯"可能失去主路割点**（2/50 张 F5 图）。它不 gate 任何进度（踩上去不换层），
   因此没有为它额外加门禁判断；如果以后给 F5 的下行梯赋予功能，需要重新评估。
2. **精英门禁可能被削弱**（250 张图 0 例；`verify_d69` 的 200 次生成里 1 例，1253:F3）。
   选择"如实降级 + 补 detour"而不是"拒绝开门"，因为：拒绝开门会重新让 **grid 依赖精英是否存在**，
   直接踩坏 D-69 A4；而单口楼梯是玩家可感知的硬缺陷，无法用"某张图不打精英"来交换。
3. **开门只补到 deg=2**：恰好两个入口，不多开；`guard < 2` 保证不会把三面墙都打开。
