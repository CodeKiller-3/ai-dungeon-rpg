## 0. 一句话结论

现在的战斗界面**不缺元素，缺的是分区和顺序**：

- 横向布局有身份带、有七格条、有回合条，但**没有战报、没有状态、没有“刚才那一下”**——三段信息全缺，玩家只能靠血条回跳猜发生了什么。
- 纵向布局有战报、有状态、有回合条，但**没有指令条**（只有一行会被裁的文本），血条还穿在角色身上。
- 两套布局的**时间轴是 100 / 150 / 180ms**：玩家这一刀和怪物那一刀隔 100ms，两个伤害数字、两条斩击弧、两次震屏全部叠在同一瞬间。这不是“快”，是“看不清”。

对标《洛克王国》真正该拿的不是它的皮肤，是它的四段闭环：**双方状态常驻 → 指令一屏可点 → 按顺序结算 → 结果逐条播报**。我们目前只做到了第 3 段。

## 1. 对标依据

### 1.1 它属于哪一类界面范式

《洛克王国》（腾讯，2010 年上线的 Flash 页游，后续有手游与“闪耀大赛”等模式）的战斗是**回合制宠物对战（monster-battler）**范式，与《宝可梦》同族。这类界面的共同骨架是四段闭环：

1. **双方状态常驻**：两边的名字、等级、血量、可用资源同时可见，不需要切页；
2. **指令选择**：底部一块面板，列出本回合可执行的动作，数量有限、一眼可点；
3. **顺序结算**：双方各出一次手，有明确的先后；
4. **结果播报**：伤害数字、状态变化、战报文本在单位身上或附近逐条出现。

我查到的公开资料里，不同版本/模式的描述不完全一致，下面只取**多份资料都成立**的部分，并标注来源类型：

由此可以确认的范式要点只有三条，而这三条恰好是我们最缺的：
- **资源标在“要花它的那个按钮”上**，而不是标在屏幕另一头；
- **状态挂在“被影响的那一方”身上**，并且**带剩余回合/层数**；
- **技能栏在下方、数量有限、可点**。

我**不引用**任何截图里的像素坐标、字号、色值、按钮数量——这些我无法核实，也不会在规格里假装知道。下文所有数字都是**我们自己的画布与代码**算出来的。

### 1.3 我抽取的 5 条可迁移原则

| 编号 | 原则 | 落到我们项目的意思 |
|---|---|---|
| P1 | 身份常驻 | 双方名字、HP、资源必须同屏，且**贴着自己那一方** |
| P2 | 指令一屏可点 | 7 个指令完整可见（含键位与代价），鼠标能点、键盘能按 |
| P3 | 代价贴在按钮上 | MP / CD / 剩余药量写在格子里，不写在顶栏 |
| P4 | 状态归属明确 | 中毒/流血贴玩家卡，狂暴/龙威贴敌人卡，带剩余回合 |
| P5 | 结果按顺序播报 | 同一回合的两次命中**不并发**，先打、再反击、再结算 |

### 1.4 明确不迁移的部分

见 §14。简单说：**不抄它的立绘对峙 + 天空背景 + 属性克制 + 4 技能槽 + 速度决定先手**。我们的题材是地牢、单角色、固定先手、MP+CD 双资源，抄错一条就会开始撒谎。

## 2. 现状基线（全部实测/读码得出）

### 2.1 两套布局的几何

`resolveBattleLayout()`（`js/core/render.js` L842–847）：`W ≥ 720 && W/H ≥ 1.20` 走横置，否则纵置。`BATTLE_LAYOUT`（L838）是默认值 `'horizontal'`，`_setBattleLayout()`（L1651）给验证页强制指定；`'auto'` 与 `'horizontal'` 同一口径（都再过一遍比例式）。`horizontalBattleGeo()`（L850–862）给出 `groundY=0.766H、playerCx=0.24W、enemyCx=0.76W`。

> 这里有个**三种形态**的问题：分派只按比例，不看高度。800×700 的宽高比是 1.14 → 走**纵置构图**，但 `W=800 ≥ 590` → 指令条又是**单行 7 格**。于是出现“纵置的分层站位 + 横置的操作区”，而纵置那套写死的 y 在 H=700 时最挤（见 G19）。规格要求：布局分派可以继续按比例，但纵置的所有纵向位置必须改为比例式，才能在任何 H 下自洽。

| 1280×800 | 1024×640 | 横置 | 490 | 246 | 778 | 96px，格宽 132 |
| 960×540 | 960×540 | 横置 | 414 | 230 | 730 | 96px，格宽 122 |

> 注意一处自相矛盾：纵置代码的版式注释写的是「1024×640 基准」（`render.js` L2730），但 1024×640 的宽高比是 1.6，会走横置——**这套基准尺寸在默认配置下永远不会出现**。实际纵置只发生在 `W<720` 或 `W/H<1.2`（如 800×900、390×844、320×568），而它的坐标却按 640 高排的。这是 G13 必须改比例锚点的根本原因：不是“可以更好”，是“基准选错了”。

### 2.2 时间轴

`battle.js` L36：`TL = { seg1: 100, lock: 150, total: 180 }`。

一次行动的完整时序：

| t (ms) | 发生什么 |
|---|---|
| 0 | 玩家扣血、`spawnHitMonster` 立刻生成飘字 + 斩击弧 + 火花；顿帧 80ms 冻结特效时钟 |
| 80 | 顿帧结束，斩击弧才走了 20ms（弧寿命 200ms） |
| 100 | 怪物段结算，第二套飘字/弧/火花生成 |
| 150 | 输入解锁 |
| 180 | 回合结束，phase 回 idle |
| 200 | 玩家那条斩击弧才消失 |
| 600 / 760 | 两个伤害数字才消失（普通 / 高伤） |

也就是：**第一刀还没画完，第二刀已经砍下来了**；两个数字同时在屏上停留 400ms 以上。

## 3. 设计目标与验收口径

先定口径，后面所有“好/不好”都按这五条判：

| 编号 | 目标 | 可证伪判据 |
|---|---|---|
| **K1 一屏可读** | “我是谁 / 敌人是谁 / 我现在能按什么 / 刚才发生了什么”四问，1 秒内可答 | 四类信息各有独立矩形区域且两两不相交；正文 ≥11px；对比度 ≥4.5 |
| **K2 指令可达** | 7 个指令完整标签在 `[0,W]` 内，鼠标 7/7 点得中 | 每格 ≥40×40；7 个文本 bbox 全在屏内且互不重叠；点击落点命中率 100% |
| **K3 状态可见** | 任一状态从施加到消失，至少有一帧可见 | 单个 chip 屏上存在时长 ≥400ms；玩家/敌人各最多 3 枚，超出折叠为 “+n” |
| **K4 节奏可分** | 同一回合内两次命中表现不并发 | 相邻两次“闪白起始”间隔 ≥180ms；伤害数字与斩击弧不同帧起（≥1 帧，约 40ms） |
| **K5 预算不破** | 战斗场景每帧新增 ≤60 次；静帧 ≤16.7ms | 与 §2.4 同口径计数；分阶段预算见 §13 |

## 4. 画面分区与比例

### 4.1 横置（W ≥ 720 且 W/H ≥ 1.20）

全部由 `groundY` 与 `H` 推出，不写死。下表给 960×540 与 1024×640 两档实数：

| 带 | 公式 | 960×540 | 1024×640 | 内容 |
|---|---|---|---:|---:|---|
| HUD | 0–28 | 0–28 | 0–28 | 不变 |
| 读数带 | 28–42 | 28–42 | 28–42 | 不变 |
| 回合管线 | `y = max(46, round(H*0.082))`，h 26 | 46–72 | 52–78 | 回合号 + 两段进度 |
| 舞台纵深 | 管线底–身份卡顶 | 72–258 | 78–334 | **只有背景，不放文字** |
| 身份卡（普通） | 底 = `min(groundY−90, groundY−mBaseH)−14` | 258–310 | 334–386 | 名字/HP/状态 |
| 身份卡（龙/大 Boss） | 同上 | 204–256 | 280–332 | 同上 |
| 精灵 | 脚底 = groundY | 324–414 / 270–414 | 400–490 / 346–490 | 不变 |
| 战报带 | `groundY+2`，h 26 | 416–442 | 492–518 | 2 行 12px，全宽 |
| 指令条 | `barH = clamp(round(H*0.178), 88, 140)` | 444–540 | 526–640 | 7 格 |

指令条内部（`barH` 内三段）：

| 段 | 偏移 | 960×540 | 1024×640 |
|---|---|---:|---:|
| header（左“行动 · 第 N 回合”，右“HP x/y · MP x/y”） | `bar.y+3 … +15` | 447–459 | 529–541 |
| 格子 | `bar.y+18`，高 `barH−32` | 462–526（64 高） | 544–608（82 高） |
| footer（悬停说明 / “1–7 或点击”） | `bar.y+barH−12 … −2` | 528–538 | 628–638 |

**为什么把战报放在地面带而不是屏幕中间**：横置的中心是两人的决斗空场，任何居中文本都会挡在刀路上；地面带 416–442 在脚底之下、指令条之上，既贴地又不挡人，读作“地面字幕”。

### 4.2 纵置（其余）

纵置改成**比例锚点**，不再用 `H−190` / `414` 这类写死值：

- `enemyGround = round(H*0.30)`
- `playerGround = min(H − barH − 8, round(H*0.72))`
- 中间信息带 = `enemyGround … (playerGround − 60)`（我方卡片顶）

| 档 | barH | 敌方脚底 | 我方脚底 | 中间带宽 | 信息带内容 |
|---|---:|---:|---:|---:|---|
| 320×568 | 150（4+3 两行） | 170 | 409 | 179 | 管线 + 战报 2 行 |
| 390×844 | 150 | 253 | 608 | 295 | 同上，垂直居中 |
| 800×900 | 96（单行 7 格） | 270 | 648 | 318 | 同上 |
| 640×640 | 114（单行 7 格） | 192 | 461 | 209 | 同上 |

> “中间带宽”= `enemyGround` 到**我方卡片顶**（`playerGround−60`）的距离——战报只住这一段，所以不会和卡片抢位置。

- 敌方身份卡：左上角，`x = 8`，`y = 32`，高 52（贴 HUD 之下，不压精灵）。
- 我方身份卡：左下角，`x = 8`，`y = playerGround − 60`（与精灵下半身同高，靠左避开居中的精灵）。
- 战报：`x = 8`，宽 `W−16`，12px，2 行，垂直居中于中间信息带（它在卡片上方，不需要为卡片让位）。
- 指令条：`cw = floor((W−52−48)/7) ≥ 70` 时单行；否则 4+3 两行。
  - 320：`cw4 = floor((320−16−18)/4) = 71`；两行格高 52，行距 6。
  - 390：`cw4 = floor((390−16−18)/4) = 89`。
  - 480：`cw4 = 111`。

这条比例式同时修掉旧版“H 越大中间越空”的问题：320×568 中间信息带 179px，390×844 是 295px，随高度增长，而两人**始终落在同一段可视区**。

## 5. 身份带信息层级

### 5.1 三段式卡片

尺寸：`w = clamp(max(spriteW×1.5 + 24, 名字宽 + 24), 112, 280)`，`h = 52`。
（名字宽用 `measureText` 实测；Boss 带【BOSS】前缀会到 9 字，13px 下约 70px，112px 卡内文本区 94px 放得下。）

| 行 | y（相对卡片顶） | 内容 | 字体/色 |
|---|---|---|---|
| L1 | 7–19 | 名字，左对齐 `x+9`；超宽用省略号，不缩字号 | 13px bold `#e8ecff` |
| L2 | 20–31 | HP 条 9px，内缩 8px；**数值叠在条内右端** | 条：我 `#4ade80` / 敌 `#e24a4a`，底 `rgba(255,255,255,0.10)`；数值 11px 白字 + 1px 黑描边 |
| L3 | 33–47 | 状态 chips，最多 3 枚，超出 “+n” | 见 §8.2 |

> HP 数值为什么挪进条里：名字和数值同排时，120px 的最低宽度只够 3 个字的名字；把数值压到条上，名字独占一行，320 宽也能完整显示“【BOSS】深渊领主”。这也是多数宠物对战界面的做法——条本身就在承担“还剩多少”的读数。

- 卡片底：`rgba(8,8,16,0.78)`；1px 边框 `rgba(255,255,255,0.20)`（`.5` 偏移）。
- 敌方狂暴：左沿 3px 竖条 `#ff9a4a`（保留现有做法，`render.js` L1292–1296）。
- **不显示“Lv.”**：`MONSTERS` 没有等级字段（`battle.js` L755 的 monster 对象无 level），写一个假等级就是撒谎。玩家侧等级已经在 HUD，不重复。

2. 命中测试读 `Render._lastBattleBox.commandBar.cells`，取第一个包含点的 cell；

判据：7 个格子中心点各点一次，7 次都触发对应 `cmd`；`Esc`/右键不做任何事。

## 7. 行动顺序可视化

### 7.1 先说实话

本作**没有速度属性**，`playerAction` 永远先结算玩家，`scheduleMonster` 把怪物段排在 `seg1` 之后（`battle.js` L675–679）。所以：

- **不画“谁更快”**，不引入“先手值”；
- 只画“**现在是哪一段**”和“**这一段走了多少**”。

### 7.2 两节点管线

尺寸：320×26（沿用现有 `battleSegments` 的框，`render.js` L244–270），位置 `y = max(46, round(H*0.082))`，水平居中。

| 区 | x 偏移 | 宽 | 内容 |
|---|---|---:|---|
| 回合号 | 0–96 | 96 | `第 3 回合`，13px bold `#ffcf6e` |
| 节点① | 96–200 | 104 | `① 你出手`，13px |
| 节点② | 204–316 | 112 | `② 怪物反击`，13px |

状态表达（三态，只用填充色 + 1px 边框，不加动画）：

| 状态 | 填充 | 文字 |
|---|---|---|
| 已完成 | `rgba(255,255,255,0.04)` | `#6b7280` |
| 进行中 | 玩家 `rgba(120,200,255,0.20)` / 怪物 `rgba(255,140,120,0.22)` | `#bfe6ff` / `#ffb1a1` |
| 未开始 | 透明 | `#8d8f9e` |

段内进度：在节点底边画 2px 高亮线，长度 = `clamp((now − segStart) / segLen, 0, 1) × 宽`。
- 玩家段：`segStart = turnRec.playerAt`，`segLen = TL.seg1`；
- 怪物段：`segStart = turnRec.monsterAt`，`segLen = TL.total − TL.seg1`；
- 时钟取 `Fx.clockNow()`（顿帧时冻结，弧和条一起“定住”，读起来是一次撞击）。

**这一段是“看得懂”的核心**：玩家按下去之后，条会从①走到②，而不是像现在这样 180ms 内两个都闪一下就没了。

## 9. 伤害数字与命中反馈的毫秒节奏

### 9.1 现状问题（可证伪）

- 两次命中的闪白起始间隔 = `TL.seg1 = 100ms` < K4 要求的 180ms；
- 伤害数字与斩击弧**同一帧**生成（`battle.js` L349 + L357 在同一函数里），数字直接压在弧的起点上；
- 血条**瞬时跳变**（`battleBar` 直接按新 ratio 填充，`render.js` L227–230），没有“掉血”的中间态。

### 9.2 目标时序（一次交锋）

| 相对时刻 | 事件 | 参数 |
|---|---|---|
| 0 | 玩家段开始；格子按下态 | 80ms |
| 0 | 命中判定完成，HP 数值已扣 | 逻辑不变 |
| 0–110 | 目标闪白 | alpha 0.60，110ms |
| 0–80 | 顿帧 | 特效时钟冻结 |
| 0–180 | 震屏 | 4px |
| 0–200 | 斩击弧 | 200ms |
| 0–160 | **HP 条缓动**（新增） | ease-out，160ms |
| 40–640 | **伤害数字**（新增 40ms 延迟） | 18/26px，−42px/s |
| 220 | 怪物段开始 | `TL.seg1 = 220` |
| 220–440 | 怪物那一套（锚点镜像） | 同上 |
| 440 | 输入解锁 | `TL.lock = 440` |
| 520 | 回合收尾，战报追加 | `TL.total = 520` |

### 9.3 时间轴改值

`TL` 从 `{100, 150, 180}` 改为 **`{220, 440, 520}`**。

- 一次交锋从 0.18s 提到 0.52s，约 1.9 回合/秒——比现在“每 180ms 一次”可读，又不会像宠物对战那样慢。
- **不改任何随机、伤害、胜负**：时间不参与判定，四策略逐局一致（同种子同结果）不受影响。
- **会触约束**：`preflight/verify_d16.html` 有两条硬断言会被打掉——
  - **B2**（L136）`lockMs > 0 && lockMs <= 160`：输入锁上限写死 160ms，改成 440 会直接判负；
  - **C 组**（L164）用 `for (k = 0; k < 240; k++) step(1)` 跨过“150ms 解锁点”，需同步改成跨 440ms。
  - A1（L105–107）读 `B.timeline().seg1` 动态比较，**不会**失败。
- 这两处必须同步更新期望值，是本规格**唯一**需要碰验证页的地方，实施前需单独确认。
- 若不接受改验证页：退而求其次的方案是保留 180ms，把怪物段的**表现**推迟到 220ms 播放，但这会要求输入锁延长到 440ms，等于还是改了 `lock`，B2 照样失败。所以“不改时间轴也不改验证页”做不到 K4，结论要写清楚。

### 9.4 HP 条缓动

- 渲染层维护 `shownHp[who]`，每帧向真实 `hp` 以 160ms ease-out 逼近；
- 数字在 **t=40** 出现（让弧先走 40ms），血条从 **t=0** 就开始缓动——两者不互相等待，各自读各自的时钟；
- 敌方/我方同一套；
- 不改 `Player.hp` / `state.monster.hp`，纯展示副本；
- 判据：缓动期间任意一帧的条长介于旧值与新值之间；160±20ms 后与真实值相等；数字首帧晚于弧首帧 ≥40ms。

### 9.5 “看得见但不糊脸”的四条硬闸

1. 单次闪白 ≤120ms（已满足，`fx.js` L102）；
2. 同屏飘字 ≤20（已满足，`feedback.js` L18）；
3. 同一目标 300ms 内不重复起震屏（新增判据；现在连续命中会重置 `shake`，导致一直震）；
4. 斩击弧与数字不同帧（40ms 延迟）。

## 13. 分阶段落地（先结构，后装饰）

每一阶段都能单独上线、单独验收；阶段之间不互相阻塞。

### S1 — 结构（不动配色、不加素材、不改时间轴）

改什么：

1. `render.js` 新增 `battleCard(ctx, cx, topY, w, spec)`，替换/扩展 `hNamePlate`（L1282–1318）为三段式；横置、纵置共用。
2. `render.js` `hCommandBar`（L1332–1358）加 `compact` 分支（4+3）；`hDrawCommandBar`（L1359–1395）加 header/footer。
3. `render.js` `_drawBattleVertical` 改用比例锚点（替换 L2861–2906 的固定值）。
4. `render.js` `_drawBattleHorizontal` 补地面战报带 + 卡内状态。
5. 两套布局共用一个 `battlePipeline()`（把 `battleSegments` 扩成带进度的版本）。

验收：

- 320×568 / 390×844 / 720×540 / 960×540 / 1024×640 五档截图；
- 几何断言：`card ∩ sprite = ∅`、`card ∩ HUD = ∅`、`pipeline ∩ card = ∅`、`log ∩ commandBar = ∅`；
- 7 个指令标签 bbox 全在 `[0,W]`；
- 每帧调用：183 → ≤ 217（结构新增 +34，见下）。

预算（最坏情况）：卡 L3 状态 3×2 方 ×3 次 = +18；管线 +8；战报 +3；header/footer +5；4+3 换行不增量。合计 **+34**，183+34 = 217 ≤ 60 余量内。

硬约束：不新增素材；不改 `TL`；不改随机；坐标全整数（`.5` 描边）。

### S2 — 交互（鼠标 + 禁用语义）

改什么：

1. `main.js` 战斗场景加 `click` / `mousemove`；`hoverIdx` 存 `ui` 状态；
2. `render.js` `hDrawCommandBar` 画 hover 边框；footer 显示 `SKILLS[id].desc`；
3. 禁用文字 alpha 0.72，代价栏写原因。

验收：

- 7 格中心点击 → 7 次 `playerAction` 正确；锁定期间点击进 `bufferCommand`；
- 键盘 1–7 行为与改前逐帧一致（同一输入序列，`turnRec.events` 相同）；
- 禁用格文本对比度 ≥4.5（按 §2.5 算式）。

预算：hover 只多 1 次 `strokeRect`；footer 多 1 次 `fillText`。**+2/帧**。

硬约束：鼠标不新增任何战斗判定；`file://` 下事件绑定与现在 `modal.js` 同路径，零构建。

### S3 — 节奏（时间轴 + 缓动 + 延迟）

改什么：

1. `battle.js` L36 `TL = {seg1:220, lock:440, total:520}`；
2. `feedback.js` 飘字 spawn 加 40ms 延迟（`bornAt` 前移/绘制时判断）；
3. `render.js` 血条缓动 `shownHp`；
4. `battle.js` L859 旁加 `state.defendAt = t0`。

验收：

- 录 3 回合，导出每次事件时间戳：相邻闪白 ≥180ms、数字与弧起点差 ≥40ms；
- 血条：缓动中间帧条长 ∈ (旧, 新)，160±20ms 后相等；
- 防御 chip ≥400ms。

预算：缓动只是同一 `fillRect` 换长度，**+0**。

硬约束：**会触 `verify_d16.html` 的 B2（`lockMs ≤ 160`，L136）与 C 组（240 帧跨 150ms，L164）**，需同步更新期望值——这是唯一需要碰验证页的改动，必须单独确认；随机与四策略一致性不受影响。

### S4 — 装饰（可选，最后做）

## 14. 我认为不该照搬的

| 《洛克王国》的做法 | 为什么不抄 | 抄了会怎样 |
|---|---|---|
| **4 个技能槽** | 我们已有 7 个固定指令（攻/防/逃/3 技能/药），键位 1–7 已上线（`main.js` L1778–1787） | 砍到 4 个会删掉逃跑或用药，直接破坏可玩性 |
| **双方的完整立绘 + 天空/草地背景** | 我们是五层地牢，靠后墙/光源/接地影建立空间（`render.js` HORIZONTAL_SCENE L874–880） | 换成插画背景，五层就只剩换色，等于放弃已有的美术资产 |
| **等级/经验在战斗内大幅展示** | 玩家等级已在 HUD；敌怪**没有等级字段** | 显示“Lv.?”或编一个数字，是假信息 |
| **速度值决定出手顺序** | 我们没有速度属性，永远玩家先手 | 画一个“谁更快”的条，等于每回合骗玩家一次 |
| **属性克制箭头 / 系别图标** | 我们只有技能倍率（1.8× / 1.2×）与防御减伤，没有元素克制表 | 画“克制/微弱”会暗示不存在的机制 |
| **PP（每技能有限次数）** | 我们用 MP + CD 双资源（`skills.js` L16–28） | 再叠一套 PP，玩家要同时管三种资源 |
| **6 只精灵的球 / 切换宠物** | 本作是单角色，没有队伍 | 画 6 个球会让人以为能换人 |
| **圆角、高饱和、粗描边的卡通风** | 我们是 84 色低饱和地牢，整体照度低（F1 地板 mean 59、墙 49；战斗后墙压暗后 mean 10） | 高饱和按钮会成为全场最亮的东西，抢走敌人 |
| **战斗内大背包面板** | 战斗只有“用药”一个道具动作（`battle.js` L864–885） | 打开背包会让回合制节奏断掉 |

**反过来，我认为现在这几件事是对的，不要为了“对标”改掉**：

- 顿帧 80ms + 震屏 4px + 闪白 ≤120ms 的组合，是“看得见但不糊脸”的正确量级，问题只在**并发**，不在强度；
- 伤害数字 18/26/36 三档与碾压环，比统一字号更能读出“这一下重”；
- 接地影按脚掌取宽（`hContactShadow`，L1265–1276），比按精灵宽度更稳；
- 龙只做“发光眼”一个身份符号（`drawDragonEyes`，L1409–1437），克制且有效；
- 84 色板不扩、敌方站台比光源暗，这两条保住了“地牢”而不是“舞台”。

## 16. 一页结论

- **该拿的**：双方状态常驻、指令一屏可点、代价贴在按钮、状态贴在被影响者、结果按顺序播报。这五条都不需要新素材，也不需要改数值。
- **最该先做的**：把横置缺的战报/状态补上，把纵置缺的七格条补上，把两套布局的固定 y 换成比例锚点。这三件事做完，界面才“同一场戏的两种摆法”。
- **最容易被忽略的**：`TL=180ms` 让两次命中必然并发——不改时间轴，后面所有特效工作都会互相打架。
- **最不该做的**：为了像《洛克王国》而换成 4 技能、加属性克制、加队伍球、加假等级。那不是对标，是换皮。

## 17. 裁定注记（2026-11-18，D-103）

**指令条格子高度以 64 定档，不采用 `barH−32`。**

- §4.1 的两处写法在本条上互相矛盾：960×540 下 `barH−32 = 96−32 = 64`；1024×640 下 `barH = 114`，`barH−32 = 82`。而 §6.2 又要求「统一外观 + 格子落点 544–608」。
- 裁定：**格高恒为 64**（紧凑档 W<590 仍为 52，那属于另一套 4+3 形态）。1024×640 的格子落点因此是 **544–608**，正好是 §6.2 区间的两端；960×540 是 462–526。
- 理由：同一套格子外观必须能在两档横置里复用。82 只在 1024×640 出现，会让同一个按钮在两种分辨率下高度不同，也使「落点 544–608」失去意义。
- 实现：`render.js` 的 `buildCommandBar` 取 `cellH = compact ? 52 : 64`，不再由 `barH−32` 推导；`verify_d102.html` 的 `d103.cellH.*` / `d103.ruling64` / `d103.ruling544_608` 断言在 `barH−32=82` 的档位仍取 64。
- 本注记只增不改：正文其余内容（含 §4.1 表格里的 82）保持原文，冲突以本注记为准。
