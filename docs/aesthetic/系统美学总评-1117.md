## 2. 逐域评分

评分口径（先定死，免得“观感一般”）：

- **R 可读性（40%）**：1× 像素、1 秒内能否读出“我在哪 / 我是谁 / 能按什么 / 刚才发生了什么”；每缺一项扣 1.5。
- **C 一致性（30%）**：同一语义跨横/纵布局、三档宽度、素材尺度是否同形同色同尺度；每出现一次“同名不同形/同形不同尺度”扣 1。
- **K 完成度（30%）**：设计基线 960×540、三档边界、极值（HP 190 的 10 颗心、龙 144、Boss 108）、状态/Boss 战是否都成立；每个硬失败扣 2。
- 总分 = 0.4R + 0.3C + 0.3K。

| 域 | R | C | K | 总分 | 判决 |
|---|---:|---:|---:|---:|---|
| 系统层（sysviz T1/X1/X3/X2/H1/H2 + 系统四页签 + HUD 读数带/状态 chip） | 8.0 | 8.0 | 7.0 | **7.7** | 达标 |
| 主菜单（首屏 + 五页 + 三档） | 9.0 | 7.5 | 4.5 | **6.8** | 部分达标 |
| 探索（地墙/装饰/12 帧/152 帧/图标 1:1） | 7.0 | 8.5 | 8.0 | **7.2** | 达标 |
| 战斗（横置/纵置、身份带、指令条、飘字、龙威、Boss 剪影） | 5.5 | 4.0 | 5.0 | **4.9** | **未达标** |
| 特效（juice / feedback / Fx） | 7.5 | 6.0 | 7.5 | **7.0** | 部分达标 |

**只算 1280×800 这一档**（大多数桌面窗口实际看到的样子）：系统 8.0 / 菜单 8.5 / 探索 7.5 / 战斗 6.0 / 特效 7.5，综合 **7.5**。
**把设计基线与窄档都算上**：综合 **6.8**。差距全部来自“高度/窄宽的边界”，不是来自美术本身。

一句话：**系统层已经像一套系统；战斗层还没有变成同一场戏的两种摆法。**

## 3. 问题清单（按严重度）

> 每条都写：现象 → 证据 → 判据 → 为什么 → 改正 → 验法 → 硬约束。
> 图路径均相对 `preflight/artifacts/aeval-1117/`。

### P1（高）纵置战斗：玩家血条横穿角色身体

- **现象**：320×568（render.js 自己写的竖屏基线）下，绿色 HP 条直接压过骑士胸口，“HP 100 / 100”被头盔/剑/盾挡掉一半。H=640 时血条在头顶上方 36px，正常；H=568 时变成穿身。
- **证据**：`narrow/11-battle-320.png`、`crops/crop-320-hpbar.png`；`js/core/render.js` L2903 `battleBar(..., 414, ...)`，L2906 `py = H - 190`（精灵占 `H-190 … H-100`）。H=568 → 精灵 378–468，血条 414–434。
- **判据**：血条矩形与玩家精灵包围盒**不相交**，且间距 ≥8px。
- **为什么算问题**：血条是战斗里最重要的读数；它压在主体上，等于每一帧都在破坏“谁在被看”。这不是口味，是遮挡。
- **改正**：在 `_drawBattleVertical` 里把玩家块做成流式：`playerBase = H - 40`（或为指令条预留 `H - 36 - 64`），`barY = playerBase - 90 - 30`；名字行跟着 `barY` 走，中段信息带用 `barY` 反推上界并 clamp。文件/函数：`js/core/render.js` `_drawBattleVertical`（L2899–2975）。
- **怎么验**：320×568、390×844、640×640 三张图；断言 `barRect ∩ spriteRect = ∅` 且 `sprite.bottom ≤ H-24`（指令条之上）。
- **硬约束**：不碰随机数、不新增素材、调用数不变。

### P2（高）纵置战斗没有七格指令条，只有一行会被裁的文字

- **现象**：横置有真正的 7 格指令条（96px 高、键位/图标/副标签）；纵置只有一行 13px 文本 `1 攻击 2 防御 … 7 用药`，在 390 宽下左边丢了“1”、右边“7 用药”被切；320 宽下两端都丢。
- **证据**：`narrow/09-battle-390.png`、`crops/crop-390-cmd.png`、`narrow/11-battle-320.png`；`render.js` L2969（纵置那行文本）、L1332–1341（横置 `hCommandBar`，`cw = floor((W-52-48)/7)`）。
- **判据**：7 个指令的**完整标签**（键位+名称）都落在 `[0,W]` 内，且每个格子的可点区域 ≥40×40。
- **为什么算问题**：用户明确要求“七格指令条”；现在两套布局给出的是两种不同的操作界面，纵置在手机上还把最后两个指令藏到屏幕外。不是风格差异，是功能可见性差异。
- **改正**：给 `hCommandBar` 加 `compact` 分支：`cw < 70` 时不画 20×20 图标，只画“数字 + 单字”（攻/防/逃/火/冲/盾/药），格高 56；或 `W < 420` 时排成 4+3 两行。保留原键位映射（L1554 的 1–7 不变）。
- **怎么验**：320/390/720 三张图；断言 7 个文本 bbox 都在屏内、无重叠；点击命中测试（若支持鼠标）落点仍在正确格子。
- **硬约束**：**每帧新增 canvas 调用 ≤60**——compact 版每格 1 个 `fillRect` + 2 个 `fillText`，7 格 21 次，安全；不加新素材。

### P3（中）纵置战斗的固定 y 锚点：H 越大，中间空得越多

- **现象**：回合条 244 / 上次行动 300 / 战报 326 / 状态 378 / 玩家血条 414 全是固定值；玩家精灵在 `H-190`。H=844 时，血条 414 到精灵顶 654 之间有 **240px（28% 屏高）** 的空地板；H=900 时更空。
- **证据**：`26-battle-v-f2.png`、`narrow/09-battle-390.png`；`render.js` L2861、L2875、L2893、L2897、L2903、L2906。
- **判据**：中段信息带底 → 玩家血条、玩家血条 → 玩家精灵，两段空隙之比 ≤1.5；当前 0 : 240。
- **为什么算问题**：不是“留白”，是布局把两个人拆到了两个不相干的区域：敌人在 90–180，玩家在 654–744，中间 470px 没有任何东西。
- **改正**：同 P1 的流式块；最小改法：`barY = Math.min(414 + Math.max(0, H - 640) * 0.55, H - 190 - 44)`，把血条随高度下移（H=568→338，H=844→526，H=900→557），随后再按 `barY` 上移状态 chip 与战报的上界。
- **怎么验**：568/640/844/900 四档，量两段空隙；再确认战报/状态条不与血条相交。
- **硬约束**：不改战斗时钟 100/150/180；不改随机。

### P4（中）纵置龙战：龙顶被 HUD 读数带压住 6px

- **现象**：龙 144px 高、脚底 180 → 头顶 36；HUD 条 0–28、读数带 28–42。头顶 36–42 这 6px 的角/翼尖被带子盖住。
- **证据**：`27-battle-v-dragon.png`、`crops/crop-v-dragon-top.png`；`render.js` L2788（Boss 高度）、L2816（脚底 `ey+90`）。
- **判据**：精灵顶 ≥44（HUD 带下沿 +2）。
- **为什么算问题**：龙是终局主体，头顶被 UI 切一刀，和“体量说话”直接冲突。
- **改正**：纵置 Boss 脚底下移 8px：`ey = Math.max(90, 44 + mBaseH - 90)`（只影响 mBaseH>108 的 Boss/龙）；或把 HUD 带在战斗场景改为 0–28（不带第二行），让出 14px。
- **怎么验**：390/800 两档龙战，扫描精灵最上行像素 y≥44。
- **硬约束**：无。

### P5（高）主菜单只有宽度三档，没有高度档：960×540 基线重叠；中档在 540 高时提示落到卡片外

- **现象**：
  1. 960×540（设计基线）走 wide：`railH = min(448, 540-152)=388`，`pipY = 112+388-40=460`；菜单 `menuY=238`，5×42 到 448，`hint.y=468`。于是 **石钉 460–480 压在提示 468 上、终点龙 414–486 压在“关于”行 406–448 上**（进度标签 452 与提示 468 只隔 16px，已经贴在一起）。
  2. 同一高度如果走 mid：`pipY=max(356,212)=356`，`p.y=398`，`p.h=min(246,132)=132`（到 530），`m.y=428`；`avail=70` → `rowH` 被下限钳到 26，5 行到 **558**（已出屏），`hint.y=578`（出屏 38px）。
- **证据**：`boundary/11-menu-root-960.png`、`crops/crop-960-overlap.png`；`render.js` L3514（三档只按 W）、L3518（railH 随 H 缩）、L3521（menuY）、L3528（pipY = railH-40）、L3530（终点龙）、L3576（hint）、L3535–3540（mid 的 p.h/hint）。
- **判据**：进度/终点与菜单行/提示**零相交**；`hint.bottom ≤ panel.bottom-8`；在 960×540 与 900×540 都成立。
- **为什么算问题**：960×540 是 `BASE_W/BASE_H`，不是冷门尺寸；在基线上菜单自己压自己，属于硬失败。根因是“只按宽度分档”，高度缩小时右栏底部与菜单底部抢同一段 y。
- **改正**：加 `compact = H < 620` 的高度档：
  - 场景 rows 3（144px），`menuY=210`，`menu.rowH ≤ 34`；
  - `progress.pipY = lay.hint.y + 26`（而不是 `rail.y+railH-40`）；
  - 终点龙在 compact 下降为 40px 并**与石钉同排右对齐**（`end.y = pipY - 8`），或按 mid/narrow 的既定做法不放替身图标、只留文字；
  - mid 的 `hint.y` 改为 `min(m.y+5*rowH+20, p.y+p.h-14)`。
  文件：`js/core/render.js` `_menuLayout`（L3512–3576）。
- **怎么验**：960×540、900×540、800×540、1024×640 四张；断言 `progress/end ∩ (menu rows ∪ hint) = ∅`，且 `hint` 在 `panel` 内。
- **硬约束**：不改 84 色素材；不引入滚动条依赖（菜单是键盘操作，不能靠滚）。

### P6（高）W=900–975 进入宽屏，但右栏需要 976，右侧被裁 76px

- **现象**：900 宽下右栏 `x=616,w=360` → 右缘 976；截图上“暂无存档”只剩“暂”，面板右边框消失，终点龙被切。960 宽时仍差 16px。
- **证据**：`boundary/12-menu-root-900.png`、`crops/crop-900-rail.png`；`render.js` L3514/3519。
- **判据**：`rail.x + rail.w ≤ W - 16` 对所有 `W ∈ [900, 975]` 成立。
- **为什么算问题**：阈值写的是 900，布局却要 976；这是“断点与几何不一致”，在 900–975 的窗口上稳定复现（不是偶发）。
- **改正**：`rail.x = Math.min(616, W - rail.w - 24)`，同时 `sc.cols = (W >= 976 ? 10 : 8)`，门列相应改；或把 wide 阈值提到 976，让 900–975 走 mid（但必须先修 P5 的高度问题，否则 960×540 走 mid 会外溢）。
- **怎么验**：900/940/975/976 四张；断言右栏完整、场景与右栏不重叠。
- **硬约束**：文档里的“W≥900”若改要同步；不改素材。

### P7（高）横置战斗没有战报 / 上次行动 / 状态 chip，龙威播报在桌面档完全不可见

- **现象**：横置只画双方名字、血条、回合条、7 格指令条；**没有** `state.lastAction`、没有最近 3 行战报、没有状态 chip。龙威升档只写进 `state.log`，因此横置（1024×640 默认走横置）玩家看不到任何“龙威升档”的字。截图 `30-dread.png` 设了 `roundNo=13`，画面里没有“龙威”二字。
- **证据**：`30-dread.png`（对比 24/25）；`render.js` L2864–2897（`lastAction`/`log`/`battleChips` 全部在纵置分支内），横置分支到 L2715 结束；`battle.js` 的龙威是 log 行。
- **判据**：在横置、龙威升档后的下一帧，画面上能找到“龙威”文本；当前 0 处。
- **为什么算问题**：这是本轮验收项里点名的一项（“龙战的龙威播报”）。系统做了，默认布局不给看，等于没做。它还让横置的“上次行动”缺位：玩家打完只看到数字，没有“谁对谁造成多少”的句子。
- **改正**：在横置加一条**单行**（不要搬整个纵置中段）：
  - 位置：`y=56`（HUD 带下 14px）右对齐到 `W-16`，或 `y=groundY+20` 的左下空白；
  - 内容：`lastAction` 一句（`你对 X 造成 N 伤害` / `X 反击，造成 N 伤害`），龙威升档时用 `#ff9b6b` 覆盖 1 行 2 秒；
  - 状态 chip 用 `battleChips` 的同款画法，横置放在 `lastAction` 下一行（最多 2 个）。
  文件：`render.js` 横置分支（L2640–2715）；数据直接读 `state.lastAction` / `state.log` / `battleChips`。
- **怎么验**：横置龙战第 13 回合截图；OCR/目视确认“龙威”；普通攻击后确认“造成 N 伤害”一行出现且不与铭牌相交。
- **硬约束**：≤60 调用——一行文字 + 2 个 chip 约 10 次，安全；不改随机/时钟。

### P8（中高）Juice 的爆发点仍按纵置坐标：横置升级/击杀特效在画面正中，不在角色身上

- **现象**：横置升级时，绿色爆发环出现在画面正中（512, 415），玩家在 0.24W=246；击杀/碾压的爆发点也在 (W/2,135)，而怪物在 0.76W=778。偏 **266px**。
- **证据**：`29-fx-level.png`（绿色环在中间，骑士在左）；`js/systems/juice.js` L99–105（`battlePoint` 固定 `W/2, H-145` 与 `W/2, 135`）。
- **判据**：`|burst.x - actorCx| ≤ 60`；当前 266。
- **为什么算问题**：Juice 是“把数值变化落到身体上”的层；落点错了，整层就从“反馈”退化成“屏幕装饰”。
- **改正**：`battlePoint(who)` 先读 `Game.Core.Render._battleLayout()`；横置用 `_battleGeo()` 的 `playerCx/enemyCx` 与 `groundY-46`，纵置保留旧值。一个函数，约 8 行。文件：`js/systems/juice.js` L99–105。
- **怎么验**：横置升级 → 环在骑士脚下；横置击杀 → 环在怪物身上；390 纵置仍正确。
- **硬约束**：无；调用数不变。

### P9（中）后墙压暗过头：五层“地点”靠道具读，空间本身只剩剪影

- **现象**：横置 F2/F5 上半屏 mean 10.4、`≤16` 90.1%（独立背景图是 18.1 / 62.4%）。F1 中央径向暗 0.62 + 墙压暗 0.28，叠加后中央墙只剩 ~27% 原亮度；F4 三根柱子内部几乎纯黑。实拍里“帐篷/木栅/王座/熔岩/棺台”都读得出，但**砖缝、拱券、柱头**在 1× 下基本消失。
- **证据**：`24/25/33/34/35-battle-h-*.png`；`render.js` L890–897（`hCenterDark`）、L906–909（`hWallDim`）、L924（0.62）、L938（0.28）、L1072（0.22）、L1130（0.30）；`d88/bg-f2.png` 对照。
- **判据**：上半屏 mean ≥14 且 `≤16` ≤80%，同时主体仍是画面最亮的 5%、熔岩/龙眼仍是最亮的 1%。
- **为什么算问题**：这不是“暗”，是**信息被压没了**：五个地方的空间语义只能靠一个道具。D-94 P7.5 的初衷是“别让背景压主体”，现在越过了平衡点。
- **改正**：只动数值，不动构图：F1 `hCenterDark 0.62→0.50`，F2 `0.55→0.46`，F4 `0.60→0.50`，F5 `0.55→0.46`；`hWallDim` 同步减 0.04。或在后墙顶沿加 1px 的 8% 亮边，给出“墙高”的读数。
- **怎么验**：重算上半屏 mean/`≤16`；与 24/25 同机位对比；确认龙眼与熔岩仍是全图 `≥170` 的唯一区域（可接受 5% 的漂移）。
- **硬约束**：不改素材、不改缩放；不要让“主体最亮”反转。

### P10（中）战斗精灵非整数缩放，同屏三种像素密度

- **现象**：普通怪 90/35=**2.571×**、玩家 90/42=**2.143×**、Boss 108/54=**2.0×**、龙 144/72=**2.0×**；`imageSmoothingEnabled=false`，所以 35 行源像素被拉成 90 行时，行高在 2/3 之间跳，边缘会出现“有的行 2px、有的行 3px”的不均匀。再加 1.25 全局缩放，设备行高在 2.5–3.75 之间跳。
- **证据**：素材尺寸表；`render.js` L2618（横置 `mBaseH=90`）、L2785（纵置 90）、L2920–2929（玩家 90）；实拍 24/25 的轮廓边缘。
- **判据**：每个战斗精灵的落屏高度 = 原生高 × 整数。
- **为什么算问题**：这是项目自己列的“非整数缩放禁令”。Boss/龙已经守住了 2×，普通怪和玩家没守住，而且恰好是出现频率最高的两个尺度。
- **改正**：统一 2×：普通怪 70、玩家 84、Boss 108、龙 144（探索仍是 1×）。若担心怪变小，统一 3×（105/126/162/216）会挤掉 640 高窗口的上下空间，不推荐。需要同步 `hNamePlate` 的 `spriteW×1.5` 与接触阴影宽度（它们已经按 `mBaseH`/`snh` 推，改后应自动跟随）。
- **怎么验**：断言 `height % nativeHeight === 0`；1× 与 8× 两张图看边缘行是否等高；1280 与 390 两档确认铭牌/阴影不脱节。
- **硬约束**：这正是满足“非整数缩放禁令”的改法；不影响 file:// 与 5 层。

### P11（中）战斗读数带把“武器有效攻击”标成“有效攻击”，玩家 ATK 11 时显示 1

- **现象**：战斗里中簇显示 `有效攻击 1`，但 `Player.atk=11`；1 是 `Inventory.atkOf(sword_rusty, lv)`（武器贡献）。探索里同一位置显示 `ATK 11 刀 1`，一进战斗就只剩“有效攻击 1”，读起来像“我的攻击力是 1”。
- **证据**：`28-fx-hit.png`、`37-status-hud.png` 顶栏；`js/systems/sysviz.js` L428–441（注释写着“战斗里改为有效攻击”，但数值取的是 `eff` 而不是 `atk`）。
- **判据**：标签为“有效攻击”时，数值 = `Player.atk`；或者标签明确写成“武器 1”。
- **为什么算问题**：这是战斗里唯一的攻击数值；它和实际伤害（D-96 后 `11²/(11+5)≈8`）对不上，玩家无法用心算验证。
- **改正**：战斗时改成 `ATK 11 · 刀 1`（与探索同形），或保留单值但改标签为“武器 1”。一行字符串，`sysviz.js` L435–437。
- **怎么验**：带不同武器/等级截三张，数字与 `Inventory.atkOf`、`Player.atk` 对得上。
- **硬约束**：无。

### P12（低）系统页 dim 数值 3.11:1，10px 下读不清

- **现象**：武器“增益 0”、龙威“未启动”等**信息性数值**用 `#5f6578`，对比度 3.11，未过 AA 4.5；9–10px 字号。

- **硬约束**：不改 84 色素材（UI 文本色不在素材板内）。

### P13（低）同一面板里两个“还差”，量级不同

### P14（低）F1 地/墙灰度比 1.22:1，五层最低

## 4. 我认为不该改的（刻意取舍，不是缺陷）

1. **84 色不扩**。素材层 84 个唯一色全部在用，前 10 色占 62.8%；这是这个项目最硬的作者性。UI 文本对比度问题用 UI 色解决，不要动素材板。
2. **FOV 5 与大面积黑场**。这是 roguelike 的取舍；1024×640 下可见区 10.6%、F2 出生点 1.3% 是它的代价。**不要**为了“填满屏幕”全局加视野半径（会直接改难度）；若真要动，只在“进入新层/新房间”做一次房间揭示，或把大窗口的逻辑视口封顶在 1024×640，而不是永久加半径。
3. **4 枚石钉 + 第五格终点符号**。第 5 格用龙图标而不是第 5 枚石钉，是刻意的层级；mid/narrow 不放替身图标也是刻意的（注释写明“不拿图标冒充”）。保留。
4. **右上角 X1 水印（F2 · 29×21 / x05 y03）**。45%/32% alpha 的“系统信号”，本来就不该抢读；360 宽下它压成 3 行也只是轻微噪音，不建议为了“更清楚”把它提亮。
5. **没有暴击系统**。这是明确的系统取舍；“碾压/高伤”是替代分级。不要为了“打击感”塞一个暴击率，那会同时打破数值口径与确定性。
6. **Boss/龙 2× 整数缩放**。108/144 是这轮最正确的尺度决定；不要为了“更大”改成 2.5×。
7. **整体低照度**。菜单 6.9、战斗 3.3 的平均亮度是作者性的暗；问题只在“后墙上限 10.4”这一处，不要把全局提亮。
8. **五层共用“两侧构件 + 中央空场”的空间语法**。这是为了决斗可读性（D-94 P2 的四条硬规则），不是偷懒；要修的是 P9 的亮度，不是推倒重画五套构图。
9. **窄屏心形退化为 HP 短条**。360 实测：`HP 100/130` 短条 + MP + 金币 + 楼层都放得下，读数不带截断；这个降级是对的。
10. **主菜单五行固定 42px + 不滚动**。键盘菜单不该靠滚动；要修的是高度档（P5），不是改成可滚动列表。
11. **纵置铭牌在怪物脚下、横置在头顶**。这是两套布局的构图差异（横置要给上方留空场，纵置要贴住中段信息带），不是不一致；只要 P4 的 6px 不切头即可。
12. **战斗背景不画满上半屏**。这是“舞台带”的构图选择；真正的问题是带内的墙太暗（P9），不是“必须铺满”。

## 6. 一页结论

- **系统层是这轮最稳的一块**：84 色、四页签、三档文本、HUD 读数带、状态 chip、1:1 图标都成立；只有“有效攻击”语义与 dim 数值两个小口子。
- **主菜单的单页质量很高，但断点没做完**：960×540 自己压自己，900–975 右栏被裁 76px。这是“高度/几何”问题，不是审美问题，能在 30 分钟内用数字验证。
- **战斗是唯一未达标的域**：纵置在 320×568 把血条压在角色身上、没有七格指令条、H>800 空 240px、龙顶被切 6px；横置则缺战报/上次行动/状态，龙威播报在桌面档完全不可见。两套布局不是“同一场战斗的两种摆法”，而是两套信息架构。
- **特效层本身是好的**：32 次调用、飘字位置正确、冻结/震屏/落点火花都在；唯一的结构性错误是 Juice 的爆发点还按纵置坐标，横置偏 266px。
- **美术没有退步**；退步的是“把美术放进不同尺寸的框里”的工程。把 P1–P8 修完，这套东西才配得上它自己的素材。
