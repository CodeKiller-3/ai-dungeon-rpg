## 2. 必修（3 项）

### B1 探索帧：AI 触发遭遇后，本帧仍继续移动

- **位置**：`js/core/main.js:1938-1957`（`_updateExplore` 内 `Game.Systems.AI.tick(player)` 之后直接进入移动分支）。
- **问题**：`AI.tick` 在怪物贴脸时同步发出 `ai:encounter`，`onAiEncounter` 会 `Battle.start` + `switchScene('battle')`；但调用方没有重新检查场景，继续执行移动、陷阱、宝箱、楼梯、遭遇判定。结果是“已经进战斗了，玩家还多走一格”。
- **证据**（一次性 CDP 探针，未落盘）：
  - 进入新局，玩家 `(1,1)`；在 `(2,1)` 放一只 `bat`（追击型）；按向下。
  - 调用一次 `Main._updateExplore(1e9)` 后：玩家 `-> (1,2)`，`Main._scene === 'battle'`，`Battle.isActive() === true`。
  - 即：场景已切战斗，移动仍然发生。
- **收益**：消除“遭遇帧多走一步”带来的连锁：战斗下踩陷阱/开箱/开楼梯确认、同帧二次 `Battle.start` 覆盖上一场战斗、步数与任务进度多记一次。
- **风险**：存档 否；战斗时序 是（遭遇帧少走一步）；验证基线 **是**。机器人会因此改变轨迹，`d38` 的 1012/1013、`d127` 的 200 局都需要重跑并重钉；1013 有可能从 `stuck` 变成 `win`，必须单独记录。
- **验证**：保留上面的探针作为一次性复现；改后同一探针应得到 `moved=false / scene=battle`。再跑 `verify_d38`、`verify_d127`，对差异逐局列出，不做“整体通过”式掩盖。

### B2 陷阱致死：死亡弹窗打开后仍继续遭遇并启动战斗

- **位置**：`js/core/main.js:2000-2017`（`Map.triggerTrap` 之后没有 `hp<=0`/弹窗守卫）；`js/systems/map.js:1875-1886`（陷阱伤害与 `battle:end lose`）；`js/systems/battle.js:887-920`（`Battle.start` 不拒绝 `hp<=0`）。
- **问题**：陷阱伤害可以把 `hp` 打到 0，`Map.triggerTrap` 同步发出 `battle:end lose`，`onBattleEnd` 走 `_finalizeDeath`（清档、打开 gameover、切回 explore）。但 `_updateExplore` 继续往下执行精英/怪物判定，发现同格有怪就 `Battle.start` + `switchScene('battle')`。最终状态是：**gameover 弹窗开着，底层却有一场活着的战斗，死亡音乐被战斗 BGM 覆盖，存档已被清空**。
- **证据**（一次性 CDP 探针，未落盘）：
  - 构造：玩家 `hp=1`，目标格放 guard 型 `slime`（AI 不主动贴脸），把 `Map.triggerTrap` 临时替换为“置 hp=0 + 发 lose”；按向目标格。
  - 关闭自适应救援时：`hp=0`、`scene='battle'`、`modal='gameover'`、`battleActive=true`、`saveHas=false`。
  - 开启自适应救援时：`hp=500`（救援成功）、`scene='battle'`、`battleActive=true`；即救援后仍立刻开战。
- **收益**：死亡路径单一出口；消除“死亡界面下活战斗”、死亡 BGM 被覆盖、清档后又被 win 写回 0 HP 存档的风险。
- **风险**：存档 是（仍走死亡清档，键名/结构不变，但不再出现异常写回）；战斗时序 是（致死帧不再开战）；验证基线 低–中（现有页大概率不覆盖该边界，但 `d38` 需要复核）。
- **验证**：同一探针改后应为 `scene='explore'`、`modal='gameover'`、`battleActive=false`。另建议在 `Battle.start` 加 `Player.hp<=0` 的防御性拒绝，并在 `_updateBattle` 开头加 `Modal.isOpen()` 早退，作为第二道闸。

### B3 巡逻怪 Motion 用数组下标做键，击杀后残留位置张冠李戴

- **位置**：`js/systems/ai.js:159-162`（`Motion.setStep('patrol_' + i, ...)`）；`js/systems/ai.js:248-252`（`removePatrolAt` 直接 `splice`，不清 Motion）；`js/systems/motion.js:56-65`（已完成条目永久保留）；`js/core/render.js:3104-3115`（按 `patrol_<i>` 取渲染位置）。
- **问题**：巡逻怪被击杀后数组 `splice`，后续怪的下标整体前移；但 `patrol_<i>` 的 Motion 条目仍属于“旧下标”的怪。新下标 `i` 的怪会拿到旧 `i` 的终点位置，而且因为“已完成条目保留”，会一直画在错误格，直到它自己下一次移动覆盖该键。可见性判定又用逻辑格坐标，于是会出现“真身在 A 格可见，却被画到 B 格”的潜行误读。
- **证据**（一次性 CDP 探针，未落盘）：
  - 设 3 只巡逻怪 `[(1,1),(2,2),(3,3)]`，给 `patrol_1` 写入已完成的插值终点 `(11,11)`。
  - 删除下标 0 后：逻辑 `patrols[1] = (3,3)`，`Motion.getRenderPos('patrol_1') = (11,11)`，`matchesLogical=false`。
- **收益**：击杀后其余巡逻怪永远画在真实格；潜行判断可信。每次巡逻怪战斗胜利后都会触发，不是罕见边界。
- **风险**：存档 否（若给巡逻怪加运行时 `uid`，不要写入 `clonePatrol`/存档，只在 `setPatrols` 重建）；战斗时序 否（纯表现）；验证基线 低（画面页可能只在过渡帧变化，`d127` 终态应不变）。
- **验证**：保留同一探针；改后 `matchesLogical=true`。跑 `verify_d95`/`verify_d73` 等画面页做像素回归，跑 `verify_d127` 确认 200 局终态不变。

### W2 玩法说明滚动状态不夹紧，超滚后出现“空按”

- **位置**：`js/core/main.js:1376-1377`（`helpScroll += 1` / `-= 1`，无上限）；`js/core/render.js:5454`（绘制时才 `Math.min` 到 `scrollMax`）。

- **证据**（同一无头环境，`getImageData` 只在末尾 flush 一次）：

  | F1 | 25×19 | 8.5ms | 39.8ms | 47.9ms | 0.9ms |

### W4 相机硬切 + 玩家 140ms 插值：每步首帧反向错位 1 格

- **位置**：`js/core/render.js:2742-2750`（相机直接取 `player.x/y`）；`js/core/main.js:1968-1969`（移动后 `Motion.setStep('player', ..., 140)`）；`js/core/render.js:3493`（玩家按插值位置绘制）。
- **问题**：移动发生在 `_updateExplore` 内；同一帧 `drawMap` 先把相机切到新格，玩家还在插值起点，于是首帧玩家相对相机反向偏 1 格，再用 140ms 滑回中心；火炬光/照明也跟相机先到新位置。视觉上像“世界先跳、角色弹回再追上”。
- **证据**（CDP 探针）：玩家 `(1,1)->(2,1)`，`Motion.setStep` 后立即 `drawMap`：相机 `camX` 已按新格算，`renderX=1`、`logicalX=2`，`firstFrameOffsetTiles=-1`（-32px）。
- **收益**：去掉每步首帧的反向弹跳与光影错位；走位观感更稳。
- **风险**：存档 否；战斗时序 否；验证基线 **高**（菜单/地图截图与位置断言都依赖固定时刻）。**依赖 W3**：缓存未解耦时不要先做相机插值。若 W3 不做，最低成本方案是“玩家也不插值、与相机一起瞬移”，用平滑度换一致；需产品取舍。
- **验证**：录 140ms 内玩家屏幕 x 轨迹，首帧偏差应为 0；`d95/d73` 连续帧截图；真机手感走查。

### W5 静态怪移动无插值，与巡逻怪 160ms 滑行不一致

- **验证**：录一段静态怪追击，逐帧看是否滑行；`d95`；`d127` 终态不变。

## 6. 做不了 / 收益存疑 / 不建议现在做

1. **真人 3 局与实机 FPS**：无头环境无法替代。W10 只能给 CPU 侧参考，必须人工在目标机器上完成；这是本轮唯一“做不了”的验收项。
2. **静态层重构（W3）**：收益取决于真机 GPU。无头 `--disable-gpu` 的 33–40ms p95 可能明显高估；先做 10 分钟真机 Performance 录制，再决定是否投入。若真机 p95 < 16ms，建议不做。
3. **相机平滑（W4）单独做**：在 W3 未解耦前单独加相机会让重建频率×8，手感更差；要么先 W3，要么维持现状。不要“先改相机再说”。
4. **拆分 6000 行 `render.js`**：零构建 + 39 个脚本顺序 + 130 页像素断言，风险远大于“文件更好看”的收益；不建议本阶段做。
5. **删除 howler / 批量改 124 个 preflight 页**：收益只有 36KB 与整洁度，风险是批量漏改；不建议。
6. **把 `Math.random` 全库清零**：地图/AI/战斗/学习器都需要随机；全库 LCG 化会重写所有系统。当前应坚持“纯绘制 0 + 粒子/战斗分流”，不要追求字面 0。
7. **绝对零网络请求**：在线 NPC 的 `fetch` 是显式可选功能；若要求任何配置下 0 请求，需要产品裁定删除该功能。默认构建已经是 0 请求。
8. **触屏支持**：已明示不支持，不算缺陷；本阶段不做。
9. **三段子页动效（W7）**：规范自己写明“若封版要求补齐，应另开卡”；收益是手感，优先级低于 B1–B3/W6，可排在后批。

## 7. 建议排卡顺序（按依赖，不按编号大小）

1. **B1 + B2 + W6 同批**：都是“状态/随机流收口”，会共同触发一次机器人基线重钉；合并成一次重钉最省，避免连续三次改基线。
2. **B3 + W5 同批**：同一套“敌人稳定 uid + Motion”机制，先修巡逻索引，再给静态怪补插值；纯表现层，风险低。
3. **W1 + W2 同批**：同一屏的滚动/排版，先量再改；960×540 目标 0 溢出，320 档保留滚动但必须夹紧。
4. **W9**：存档失败提示，独立小卡，不依赖上面的基线。
5. **W3 → W4**：先真机 Profile；确认值得后再做静态层解耦，最后才做相机平滑。
6. **W7 / W8 / O 系列**：按答辩时间决定；W8 必须单独重钉，不与玩法卡混。

**一句话总结**：当前最危险的不是“慢”，而是“状态已经变了、调用方还在往下跑”（B1/B2）和“击杀后怪物画在错误格”（B3）；性能上唯一值得先量化再动手的是静态层每步重建（W3），而它又是相机平滑（W4）的前置条件。
